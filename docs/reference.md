# Справочник архитектуры и возможностей CocoaSkills

Документ содержит подробное справочное описание матрицы установки, зависимости скиллов, манифестов команд, компилируемых команд, системы аудита безопасности и настройки окружения разработки.

CocoaSkills является независимой реализацией открытой спецификации [Curator Protocol](https://github.com/relux-works/curator-spec). Исполняемый файл `csk`, имя пакета и имена каталогов состояния сохраняют имена совместимости конкретной реализации. Портативные манифесты и маркеры следуют общему протоколу.

## Матрица вариантов установки

Установщик поддерживается на платформах macOS, Linux и Windows. Компилируемые команды `go-repository-v1` поддерживаются только на macOS и Windows. На Linux установщик отклоняет скилл с такой командой до проверки учётных данных и до запуска воркера.

### pipx

Рекомендуемый способ установки изоляцией в отдельное окружение:

```bash
pipx install cocoaskills
```

Команда устанавливает исполняемый файл `csk` в глобальный каталог бинарных файлов.

### uv tool

Установка через менеджер `uv`:

```bash
uv tool install cocoaskills
```

Команда изолирует пакет и регистрирует точку входа `csk`.

### Homebrew

Установка на macOS и Linux из стороннего тапа:

```bash
brew tap ivanopcode/csk
brew install cocoaskills
```

Пакетный менеджер устанавливает утилиту и необходимые зависимости.

### mise

Установка через универсальный менеджер инструментов:

```bash
mise use -g pipx:cocoaskills@latest
```

Команда регистрирует `csk` в глобальном окружении пользователя.

### Скрипт быстрой установки

Автоматическая установка через интернет:

```bash
curl -fsSL https://cocoaskills.org/install.sh | sh
```

Скрипт определяет наличие Python, отдает приоритет `pipx` и `uv tool`, а при их отсутствии выполняет `pip install --user`. Проверяйте содержимое скрипта перед запуском.

### Установка через pip

Прямая установка в пользовательский каталог:

```bash
python -m pip install --user cocoaskills
```

Команда копирует пакет в каталог пользователя и создает точку входа `csk`.

## Зависимости скиллов

Пакет скилла объявляет требования к другим скиллам в файле `agent-skill.json` (схема v4) в секции `dependencies.skills`.

Пример объявления зависимости:

```json
{
  "schema_version": 4,
  "runtime_roots": ["scripts"],
  "capabilities": { "exec": ["trk", "git"], "network": "none" },
  "commands": {
    "report": { "type": "script", "unix_path": "scripts/report" }
  },
  "dependencies": {
    "skills": {
      "skill-tracker": {
        "git": "git@gitlab.example.com:skills/skill-tracker.git",
        "ref": { "kind": "tag", "value": "v1.4.2" },
        "mode": "runtime",
        "commands": ["trk"]
      }
    }
  }
}
```

Манифест объявляет зависимость от скилла `skill-tracker` с тегом `v1.4.2`.

### Режимы активации зависимостей

Режим `mode` определяет состав элементов, передаваемых от провайдера к потребителю:

* `full`: режим по умолчанию. Активирует контекст промпта и все экспортируемые команды провайдера.
* `runtime`: активирует только команды. Массив `commands` сужает активацию до указанных экспортов.
* `context`: активирует только контекст промпта без экспорта команд.

Установщик `csk install` рассчитывает транзитивное замыкание зависимостей, приводит дублирующиеся требования к единому ref и упорядочивает провайдеров перед потребителями. Несоответствия версий, конфликты URL и циклические зависимости вызывают ошибку установки. Выборочные операции с флагом `--only` ограничивают действия конкретным скиллом: выбранный скилл затягивает свои обязательные зависимости в замыкание исполнения, а невыбранные декларации на диске остаются без изменений.

### Локальная подмена и белые списки источников

Локальная разработка и контроль источников поддерживаются двумя механизмами:

* `Skillfile.dev.json` подменяет провайдеров локально путем указания пути к рабочей копии или git-ссылки. Файл не отслеживается в git. Строгий режим аудита отвергает установки с активными подменами.
* Параметр `allowed_sources` в `~/.cocoaskills/config.json` задает разрешенные префиксы `host/path` для git-источников. Установщик нормализует SSH и HTTPS URL для проверки идентичности источника.

## Порядок разрешения исполняемых shims

При вызове команды агентом система ищет исполняемый файл по цепочке приоритетов:

1. Проектные shims в `<repo>/.agents/bin/<command>`.
2. Глобальные shims в `<csk-home>/global/bin/<command>`.
3. Системные бинарные файлы, проверенные манифестом.

Интеграция с оболочкой через `csk shell-init --install` создает скрипт автозагрузки для добавления путей бинарных файлов в переменные окружения.

При вызове `csk global install` установщик публикует исполняемые форвардеры в пользовательский каталог бинарных файлов (`~/.local/bin/` на Unix или `%USERPROFILE%\.local\bin` на Windows) для прямого вызова глобальных команд из командной строки. При включении интеграций OpenCode или Windsurf в глобальной конфигурации установщик автоматически связывает глобальные скиллы в пользовательские директории агентов (например, `~/.agents/skills/`).

## Манифесты команд скиллов

Файл `agent-skill.json` объявляет команды, разрешения аудита и зависимости скилла.

### Эволюция схем манифеста

Схемы манифеста развиваются по версиям:

* Схема v2: добавляет поддержку многофайлового хранилища через `runtime_roots`.
* Схема v3: добавляет конверт разрешений аудита `capabilities`.
* Схема v4: добавляет секцию зависимостей скиллов `dependencies.skills`.
* Схема v5: добавляет секцию требований к MCP-серверам.
* Схема v6: добавляет компилируемые команды и исключение файлов сборки через `build_roots`.
* Схема v7: добавляет зафиксированные внешние git-репозитории сборки через `go-repository-v1`.
* Схема v8: добавляет объявленные корни first-party модулей `modules` на команде `go-v1` и пару `execution_policy` + `interpreter` на script-команде.

### Пример смешанного манифеста

Манифест схемы v6 объединяет скриптовые, компилируемые и системные команды:

```json
{
  "schema_version": 6,
  "runtime_roots": ["scripts"],
  "build_roots": ["build"],
  "capabilities": {
    "network": "none",
    "filesystem": "repo",
    "exec": ["git"],
    "secrets": "none",
    "env_read": [],
    "prompt_scope": "Inspect a repository and produce local reports."
  },
  "commands": {
    "format-report": {
      "type": "script",
      "unix_path": "scripts/format-report",
      "win_path": "scripts/format-report.cmd"
    },
    "repo-report": {
      "type": "build",
      "driver": "go-v1",
      "source_dir": "build/cmd/repo-report"
    },
    "git": {
      "type": "system",
      "command": "git",
      "hint": "Install Git through project bootstrap tooling"
    }
  },
  "dependencies": {
    "commands": {},
    "mcp_servers": {},
    "skills": {}
  }
}
```

Конфигурация задает скрипт `format-report`, Go-инструмент `repo-report` и системный бинарный файл `git`.

## Компилируемые команды

Схема v6 поддерживает компиляцию исполняемых файлов с помощью драйвера `go-v1`.

Драйвер `go-v1` использует вендоренные зависимости и отключает сетевой доступ во время сборки. Валидация пакета отвергает смену инструментария, cgo, PGO, кодогенераторы, тесты, ассемблерные файлы и внешнюю линковку.

### Корни first-party модулей схемы v8

Команда `go-v1` схемы v8 объявляет `modules`: каталоги first-party Go-модулей
того же пакета, которые корень сборки заменяет через `replace`. Менеджер
проверяет объявление по снапшоту до фиксированного `go list`, читает
эффективный набор `replace` только из `<корень сборки>/vendor/modules.txt`
после `go list` и до `go build`, допускает лишь форму "каталог" без версий с
обеих сторон и требует взаимно однозначного соответствия объявленных каталогов
и эффективных директив. Объявленные каталоги входят в поверхность сканирования
вместе со своими vendor-копиями; послабление для аудированного стороннего
vendor-кода к заменённым модулям не применяется. Установка схемы v8 записывает
install marker schema 4.

Политику выполнения `script-worker-v1` csk не реализует: script-команда, которая
её выбирает, отклоняется с `script_execution_policy_unsupported` на установке и
в `csk check` и никогда не публикуется как declared-only shim.

Процесс сборки выполняется через изолированный воркер `manager-worker-v1`. Менеджер проверяет идентичность воркера перед выдачей авторизации на сборку. Скомпилированные артефакты сохраняются в защищенном кэше `<csk-home>/builds/go-v1/` и исполняются через сгенерированные shims. Полный контракт сборки, структуру хранения кэша, протокол передачи воркера и границы безопасности см. в разделе [Schema-6 build contract](../ARCHITECTURE.md#schema-6-build-contract).

## SSH-креды внешних репозиториев сборки

Секция `build_ssh` глобального файла конфигурации `~/.cocoaskills/config.json` хранит параметры аутентификации оператора для скоупов канонической идентичности репозиториев сборки:

```json
{
  "build_ssh": {
    "gitlab.example.com": {
      "identity": "~/.ssh/personal"
    },
    "gitlab.example.com/portals/infra": {
      "agent": "auto",
      "identity": "~/.ssh/work.pub"
    }
  }
}
```

Правила обработки записей:

* Грамматика скоупа включает имя хоста `host` в нижнем регистре и опциональные сегменты пути. Сопоставление выполняется исключительно по целым сегментам с разделителем `/` (например, скоуп `portals` не покрывает `portals-evil`). При совпадении нескольких правил выбор определяется наиболее длинным скоупом (longest-prefix match).
* В каждой записи требуется указать минимум одно из полей `agent` или `identity`. Указание обоих полей формирует запись типа pinned-agent (агент хранит приватный ключ, а публичный ключ `.pub` определяет предъявляемый ключ). Данная конфигурация рекомендована при активном SSH-агенте и является третьей канонической формой аутентификации спецификации Curator Protocol.
* Порядок приоритета источников данных: параметры командной строки `--build-ssh-*` имеют высший приоритет, переменные окружения `CSK_BUILD_SSH_*` перекрывают настройки конфига, а скоупы конфигурационного файла применяются при отсутствии флагов и переменных. Манифест скилла не имеет права выбирать или запрашивать креды.
* Ключи структуры должны быть уникальными. Любая невалидная или синтаксически некорректная запись приводит к ошибке загрузки файла конфигурации (режим fail-closed).

Параметры аутентификации применяются индивидуально для каждого репозитория: в рамках одной операции установки разные репозитории сборок могут использовать различные SSH-ключи. Подробное описание контракта содержится в документе [Внешние репозитории сборки](external-build-repositories.md).

## HTTPS-токены внешних репозиториев сборки

Секция `build_https` глобального файла конфигурации `~/.cocoaskills/config.json` хранит выбор источника токена оператора для скоупов канонической идентичности репозиториев сборки:

```json
{
  "build_https": {
    "gitlab.example.com/portals/infra": {"token": "git-credentials"},
    "gitlab.example.com/vendor": {"token": "keyring", "username": "oauth2"},
    "ci.example.com": {"token_env": "CI_TOKEN"}
  }
}
```

Правила обработки записей:

* Грамматика скоупа совпадает с `build_ssh`: хост в нижнем регистре и опциональные сегменты пути, сопоставление по целым сегментам `/`, при нескольких совпадениях побеждает самый длинный скоуп.
* Каждая запись выбирает ровно один источник: `token: "git-credentials"` (существующая HTTPS-запись оператора для хоста), `token: "keyring"` (токен, сохраненный командой `csk config build-https login`) или `token_env` (переменная окружения, читаемая на входе в процесс). Литеральный секрет в конфигурации отклоняется при загрузке файла (режим fail-closed).
* Порядок приоритета: переменная окружения `CSK_BUILD_HTTPS_TOKEN` перекрывает любой скоуп на один запуск (с необязательными `CSK_BUILD_HTTPS_USERNAME` и `CSK_BUILD_HTTPS_HOST`; без пина хоста токен передается каждому HTTPS-хосту замыкания установки). Флагов для этой поверхности не существует. Манифест скилла не имеет права выбирать или запрашивать креды.
* Отсутствие совпавшего скоупа не является ошибкой: анонимный HTTPS остается рабочим транспортом, и публичный репозиторий выкачивается как раньше.

Креды читает менеджер до fetch через `git credential fill/approve/reject` при отключенных интерактивных запросах; брокер, запиненный на один хост, отвечает только на два промпта Git и завершается без вывода на любой другой ввод. Подробное описание контракта содержится в документе [Внешние репозитории сборки](external-build-repositories.md).

## Аудит безопасности и реестры

Команда `csk audit` оценивает правила безопасности на снимках скиллов.

### Режимы проверки аудита

Флаг `--audit` при установке регулирует режим проверки:

* Режим Advisory (по умолчанию): выводит предупреждения при обнаружении рисков и продолжает установку.
* Режим Strict (`csk install --audit strict`): прерывает установку, если уровень риска достигает или превышает целевой порог.

### Реестры аудита

Реестры аудита распространяют подписанные утверждения о коммитах и хэшах скиллов. Реестры настраиваются в файле `~/.cocoaskills/config.json`:

```json
{
  "audit_registries": [
    {
      "name": "internal",
      "url": "https://registry.example.com",
      "public_keys": ["ed25519:base64key..."]
    }
  ],
  "disable_builtin_registries": false
}
```

Установщик `csk install` проверяет подлинность записей с помощью публичных ключей Ed25519. Подтвержденные отзывы блокируют установку.

Системная конфигурация `/etc/cocoaskills/config.json` (или `%ProgramData%\cocoaskills\config.json` на Windows) задает корпоративные настройки. Заблокированные ключи системного файла перекрывают настройки пользователя.

### Ограничения безопасности

Распаковка архивов отвергает symlinks, выходы за границы каталога, коллизии путей, архивы с количеством файлов более 100 000 и объемом несжатых данных более 512 МиБ. Сетевые запросы к реестрам ограничены размером 16 МиБ на ответ и 10 000 записей на запрос.

## Окружение разработки и сборка пакета

Для разработки CocoaSkills требуется Python 3.11 или новее.

### Настройка окружения

Команды настройки локального окружения:

```bash
git clone https://github.com/ivanopcode/cocoaskills.git
cd cocoaskills
python -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
python -m pytest
python -m mypy
```

После выполнения команд виртуальное окружение активировано и зависимости разработки установлены.

### Сборка дистрибутива

Команды сборки и проверки пакетов:

```bash
python -m build
twine check dist/*
```

Сборщик создает файлы sdist и wheel в каталоге `dist/`.

Пакет не использует сторонние runtime-зависимости. Версия определяется автоматически из git-тегов через `setuptools-scm`.
