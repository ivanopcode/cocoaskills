# CocoaSkills RFC 0009: Skillfile schema 2 sources (draft, opt-in)

Status: draft
Date: 2026-09-18
Author: Ivan Oparin
Target: v0.16.0

Schema 1 skills name one local source each. Schema 2 names a map of
sources once and selects skills from them, so a project can mix local
directories, Git endpoints and canonical repository identities under
one lock. This RFC records the draft, opt-in implementation against
curator-spec `8ba9c235ec5be00d52378479516c82386fd0c178`. The feature
carries no release qualification and no conformance claim.

## 1. Overview

- Schema 2 is accepted only with the opt-in: the global config
  declares `"experimental": {"skillfile_sources": true}` or the
  environment sets `CSK_EXPERIMENTAL_SKILLFILE_SOURCES=1`. Without it
  the CLI keeps released v1 behaviour byte-identically, including
  error text and help output.
- A `sources` map binds aliases to `path`, `git` or `repository`
  acquisitions. Skills are legacy entries, individual selectors or
  collection selectors; the three forms mix in one list under one
  name namespace.
- The CLI mapping reuses the existing commands: `csk install` is
  initial resolve+install or locked install, `csk upgrade` is the
  explicit refresh, `csk status` is read-only currentness, and the
  draft-only `csk check` validates a schema-2 Skillfile without
  installing. Launch reads installed state and never rescans live
  inputs. Install and upgrade acquire path sources only; network
  acquisition is not implemented in this draft.
- Network acquisition follows a machine-owned `source-policy.json`
  beside the global config. Schema 1 lists endpoints per exact
  repository identity; schema 2 adds ports, mirrors and aliases.
- `Skillfile.lock.json` freezes resolved members and snapshots;
  machine-private bindings live under the csk home. Only `csk
  upgrade` replaces the lock.
- Failures render as thirteen stable classes with the selector or
  member, the reason and one remediation line, never a secret.
  Schema failures precede filesystem and network work.

## 2. Motivating case

A team keeps reviewed skills in one local directory, team skills in a
Git repository, and vendored skills under pinned identities. Schema 1
forces one source spelling per skill with no shared lock and no
machine policy for endpoints. Schema 2 declares the three sources
once, selects individual skills and whole collections from them, and
locks the result, while the machine owner controls endpoints, ports,
mirrors and aliases outside the Skillfile.

## 3. Proposal

The manifest parser accepts `schema_version` 2 with the opt-in and
parses `sources` plus the three skill forms. Structural validation is
hand-written against the draft schemas; production code never depends
on a schema validator. Git declarations follow the closed core 6.3
endpoint grammar: `https://` carries no userinfo, password or port,
while `ssh://` and scp spellings may carry a username. Branch refs
are admitted only in the root project Skillfile.

Collection selectors enumerate members with `include` and `exclude`
and freeze membership in the lock. `root_inputs` allowlists, per
source alias, what the `"."` directory may admit, so root selection
stays explicit.

The transport planner resolves each network identity to an ordered
endpoint plan purely: no I/O runs during planning. Acquisition over
those endpoints is specified but not implemented in this draft:
install and upgrade refuse `git` and `repository` sources, and only
`csk check` exercises the planner. Policy load distinguishes absence
(allowed) from an invalid or unreadable document, which fails
`repository_policy_invalid` before any network I/O.

Install captures immutable snapshots of path sources under the
`source-v1` home namespace, stages the desired state, and commits
lock, markers, runtime, context and adapters in one atomic
transaction; any failure leaves the previous state byte-identical.
Status stages the locked desired state in a temporary directory and
compares live targets without writing. Check parses, plans and
verifies the lock without traversal or acquisition.

The renderer maps each stable class to one remediation line.
Refusals name the source alias, the field and the shape of the
violation without echoing the declaration, and endpoint subjects
render from parsed scheme, host and path; absolute paths redact to
`<path>` as a second line of defence. One constant holds the
`draft skillfile-sources-v1 (opt-in)` label; every user-facing
surface prints it verbatim.

## 4. Compatibility

Frozen v1 wire schemas, release artifacts and the released suite pin
stay byte-unchanged. The draft adds one conditional subcommand,
`csk check`, which exists only with the opt-in; without it the
parser, help texts, exit codes and error bytes equal the release.
A present-but-unloadable config renders the v1 shape on every
surface: the parser is the released v1 parser, so `check` is not
parseable and no draft label or paragraph can render. Where a command
actually runs, dispatch loads the config again and the refusal names
the config with the reason. Schema 1 projects never read the policy,
the lock or the snapshot store.

## 5. Bounds

Selection requires descriptor-relative traversal and is POSIX-only;
runtimes without the mechanism get a structured refusal, never a
best-effort walk. Installs publish context only: members exporting
commands or declaring skill requirements are refused. The global
scope stays on schema 1. Network acquisition is not implemented:
`git` and `repository` sources validate and plan, but install and
upgrade refuse them. The legacy configured-Git directory agreement
is strict on write and tolerant on read, per
UNRESOLVED_QUESTIONS.md. None of this is release-qualified and none
of it claims conformance; the operator guide states the same bounds
in [skillfile-sources.md](skillfile-sources.md).

### Addendum (2026-09): Windows source selection

The POSIX-only traversal decision above is superseded. Schema-2 selection
now uses the POSIX descriptor-relative backend or a Windows backend based on
held NT handles, `NtCreateFile`, file-ID identity and handle-based directory
enumeration; symlinks and junctions are read through `FSCTL_GET_REPARSE_POINT`.
Other reparse tags remain fail-closed. This addendum replaces only the
platform bound; the other RFC bounds remain in force.
