## Проблема (кратко)

ytx пишет debug-логи в stdout, перед JSON-результатом. Даже при погашенном stderr (2>/dev/null) на stdout остаются строки вида "2026-... [debug] Making API request ..." до JSON. Поэтому json.loads(stdout) падает с "Extra data", и агент не может распарсить результат команды, включая id созданной задачи в issue create. Приходится уходить в фолбэк через поиск, который сам ненадёжен: индекс YouTrack отстаёт (только что созданная задача не находится несколько секунд), фулл-текст шумит (запрос по summary токенизирует agent и отдаёт сотни мусорных хитов по всему инстансу), а id не угадать (счётчик проекта общий на много команд). Это нарушение операционного контракта скиллов: Level 2, детерминированный парсируемый вывод и диагностика в stderr, а не в stdout.

## ТЗ

1. Разделение потоков. Все логи (debug, info, warn), прогресс и диагностика пишутся только в stderr. stdout содержит ровно один валидный JSON-документ, результат команды. Касается всех подкоманд ytx (instances, board, issue и т.д.). Проверить конфигурацию логгера и хендлеров: убрать вывод в stdout, направить в stderr.

2. issue create возвращает id и url. На --apply ответ create содержит на верхнем уровне идентификатор созданной задачи (idReadable, например PMA-12345) и url. То же для create-subtask и board create-task, create-subtask. Чтобы агент читал id напрямую из stdout, без поиска.

3. Машинный режим по умолчанию. stdout это JSON всегда. Если нужен человекочитаемый вывод, он идёт под явный флаг (--pretty или --human) и не ломает JSON-режим. Опционально --quiet глушит даже stderr-логи.

4. Подтверждение записи без поиска. В рекомендованном флоу (SKILL.md и доках) подтверждать создание и обновление через fetch-by-id (issue show id), а не через issue search: id консистентен, индекс поиска eventually-consistent. Зафиксировать это правило в SKILL.md.

5. Защита от дублей (опционально, если дёшево). issue create --dedupe-by-summary: если в проекте или борде уже есть открытая задача с тем же summary, не создавать дубль, а вернуть существующий id с пометкой. Снимает риск слепого ретрая, когда агент не получил id.

6. Точечный поиск. issue search: поддержать scoped-запрос (project key) и/или флаги project, mine, recent, чтобы при необходимости поиск был точным, а не фулл-текст по всему инстансу. Документировать, что для подтверждения записи search не используется (см. п.4).

7. Тесты. Юнит и смоук: stdout каждой команды парсится как один JSON; debug-логи присутствуют только в stderr; issue create --apply возвращает id созданной задачи; dedupe не плодит дубль.

## DoD

- Любая команда ytx: вывод `cmd 2>/dev/null` парсится как ровно один JSON-документ без ошибок.
- Ни одной debug или info строки в stdout ни у одной подкоманды; вся диагностика в stderr.
- issue create --apply (и create-subtask, board create-task, board create-subtask) возвращают idReadable и url созданной задачи на верхнем уровне JSON.
- В SKILL.md зафиксировано: подтверждать запись через issue show id (fetch-by-id), не через search; search только scoped.
- Если делается: --dedupe-by-summary возвращает существующий id вместо дубля, покрыто тестом.
- Если делается: issue search поддерживает project-scope; фулл-текст по всему инстансу не используется в дефолтном флоу.
- Тесты на разделение потоков и на возврат id зелёные.
- Ручной прогон: создать задачу через ytx, прочитать id напрямую из stdout, подтвердить через issue show, без обращения к search.
